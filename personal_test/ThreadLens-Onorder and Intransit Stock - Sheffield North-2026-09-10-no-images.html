Hi Marie,

I checked the code and it's an implementation issue at the Stock Master end. We expected that if we process the onOrder and inTransit buckets in the same execution, only one event would be published with both bucket updates and reach to data lake. However, the current implementation creates two separate events.

The root cause is that while processing a zero-down position for the onOrder and inTransit buckets, we are not updating record versioning. Consequently, when these events are published to SNS, the onOrder event successfully reaches the data lake, but the inTransit event is discarded because it is counted as a duplicate, arriving within five minutes of the onOrder event.

So As next steps, we are fixing this issue in the Stock Master implementation to add versioning for each update. Since the next store rollout is on the 15th/16th, if we are unable to fix this issue by then, we will update the production cutover activity. This update will involve zeroing down the onOrder bucket independently, waiting for 10 minutes and then processing the inTransit bucket independently. This sequence will prevent the duplication issue, as the constraint at the SNS level is only 5 minutes.

Another option we have for Woking and Sheffield Stores is to extract older events from CloudWatch logs on the Stock Master side and republish them, but this would require 1-2 days from our side. So can you please confirm with the Datalake team if reprocessing older timestamped events will cause any issues on their end?

I'm happy to schedule a call to discuss this further. 

Thank you
Siddharth Shah
